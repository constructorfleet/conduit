# Barge-In Is Keyword-First

Barge-in — cutting off the assistant by speaking over it — ships first as a
**spoken keyword handled on the device**, not as an open-ended voice-activity
detector listening to the server-side audio stream during playback.
[ADR-0014](0014-voice-activity-detection-as-two-decisions.md) split voice
activity into a silence-trimming input stage and barge-in, and deferred the
barge-in protocol to "its own ADR". This is that ADR. It does **not** decide the
duplex-audio protocol; it decides that barge-in does not need one to ship, and
that the open-ended detector — the thing that needs it — is deferred again,
behind the same protocol question, with the reasons written down.

The framing in issue #105 and ADR-0014 both read barge-in as one feature blocked
on one decision: how does audio reach the server while the assistant is
speaking. That is the right question for an energy-VAD barge-in, and the wrong
question for the barge-in people actually ask for first — "let me say *stop* and
have it stop". Reading the firmware rather than the server makes the split
obvious, the same way reading the audio path in frame order did in ADR-0014.

**The device already hears "stop" during playback**

Both shipped configurations carry a `stop` microWakeWord model, and it is not
subject to the audio path that `Command::End` tears down. In
`firmware/esphome/conduit-voicepe.conduit.yaml` (and the sat1 equivalent), the
`micro_wake_word:` block runs on its own microphone tap with its own
`gain_factor`, declares `stop_after_detection: false` and `vad:`, and lists a
`stop` model (`id: stop`, `internal: true`) rendered from the pipeline per
[ADR-0015](0015-render-the-conduit-part-of-the-firmware.md):

```yaml
- model: .../stop.json
  id: stop
  internal: true
```

`micro_wake_word` infers on that tap independently of `conduit_voice`'s state
machine. The reason no audio reaches the server during playback — the
`conduit_voice` component stops streaming once it enters `REPLYING`, and
`crates/conduit-api/src/converse.rs` drops any frame arriving after
`Command::End` — does not touch the wake tap at all. So the detector barge-in
needs does not have to be built, attached to a stream that does not exist, or
fed by a protocol that does not exist. It is already running. What is missing is
that its detections are thrown away.

`on_wake_word_detected` routes **every** match to `conduit_voice.start` without
branching on which model fired:

```yaml
on_wake_word_detected:
  - if:
      condition:
        switch.is_off: master_mute_switch
      then:
        - conduit_voice.wake_debug_event: { id: conduit }
        - conduit_voice.start: { id: conduit }
```

so a spoken "stop" is discarded today. Making that routing model-aware — the
`stop` model, while a turn is running, calls `conduit_voice.interrupt` instead
of `conduit_voice.start` — reaches `Command::Stop`, which already cancels the
turn (`converse.rs`, `conduit-runtime/src/turn.rs`). That is keyword barge-in
over machinery that already ships. This is a render change, not a hand-edit:
per ADR-0015 the fragment is generated by
`GET /v1/devices/{device}/firmware` and asserted by
`cargo test -p conduit-api --test firmware_fragments`, so the branching logic is
added to the renderer and the checked-in fragment moves with it.

**Decision one: barge-in is a spoken keyword, handled on the device**

The first barge-in Conduit ships is the `stop` model routed to
`conduit_voice.interrupt`. It is a device/transport concern, not a pipeline
stage: nothing new is added to the graph, no `NodeKind` and no
`ProviderCapability` gains a variant, and the server sees an ordinary stop
command it already knows how to act on. This is deliberately the **opposite**
placement question from ADR-0014's silence trimmer, which *is* a graph node —
barge-in occupies no stage position in `turn.rs::listen` because, as ADR-0014
established, `listen` has already returned by the time playback begins.

This sidesteps the hazard ADR-0014 flagged as possibly fatal to naive barge-in:
echo. Conduit performs no acoustic echo cancellation, the mic and speaker on an
ESP32-S3 are inches apart, and during playback the assistant is *always*
speaking — so an energy detector asked "is anyone talking" is at war with itself
from the first frame. A keyword model asked "did someone say *stop*" is far more
robust to the assistant's own voice. The residual failure is narrow and
testable: the assistant itself saying the word "stop". That is a bounded,
documented limitation, not an open echo problem.

**Decision two: a voice interrupt emits `BargeIn`, which needs a wire bit**

Today `conduit_voice.interrupt` sends `Command::Stop`, and the server cancels
with `CancelReason::UserRequested` (`converse.rs`, `turn.rs`). A keyword
barge-in arriving that way would be recorded as `UserRequested`, and the
`barge_in` metric label would stay dark — the same silence `README.md:522-531`
warns operators about.

A *voice* interrupt emits `CancelReason::BargeIn`. That reason exists precisely
for voice detected over the assistant (`README.md:524`), and every downstream
consumer is already in place per ADR-0014: the terminal variant
(`conduit-core/src/event.rs`), the metric mapping
(`conduit-metrics/src/collector.rs`), and the wire contract
(`frontend/src/contracts/events.ts`). Nothing new is emitted; an existing,
unemitted reason finally gets an emitter.

Distinguishing the two requires the device telling the server which kind of stop
this is — a button press versus a heard keyword. This is the one genuine
protocol addition here, and it is small: a reason discriminator on the stop
command, defaulting to `UserRequested` so a satellite that does not send it (or
an older one that cannot) behaves exactly as today. A button-press stop stays
`UserRequested`; only the `stop`-model route sets the barge-in discriminant.
This is additive and negotiation-free, in contrast to the duplex-audio options
below.

**Decision three: open-ended barge-in stays deferred, behind the same door**

The energy-VAD barge-in — noticing *any* sustained speech over the assistant,
not just a keyword — is not decided here, and does not begin until the
duplex-audio question ADR-0014 deferred is answered in its own right. Its two
hard problems are unchanged by this ADR and are the reasons to keep it deferred:

- **It needs the audio path this ADR avoids.** An energy detector must hear the
  room during playback, which is exactly the stream `Command::End` tears down.
  That is still a device-protocol change with a backward-compatibility story for
  deployed satellites, and it still belongs in its own ADR. Under issue #122 —
  rendering the firmware from the pipeline — the negotiated-
  capability option loses its only advantage, because server and firmware version
  together and the change becomes a deletion rather than a negotiation; that is
  the better time to decide it.
- **Echo is unresolved for it.** The keyword path dodges echo; the energy path
  does not. Deciding it means choosing a posture — device-side AEC, a stated
  hardware assumption, or output-referenced suppression — and under #122 that
  becomes "which board profiles declare AEC", a sharper question than the one
  #105 is currently stuck on.

The fire-threshold question ADR-0014 raised — how much sustained speech, for how
long — is an energy-VAD question. It has no meaning for a keyword model, whose
own detection threshold governs, so it is deferred with the detector rather than
answered here.

**Verification gates**

Two firmware assumptions this decision rests on are read from the ESPHome
configuration, not yet confirmed on hardware, and each is cheap to check and
decides whether the keyword path works at all:

- `on_wake_word_detected` exposes which model matched, so the routing can
  branch on the `stop` model.
- `micro_wake_word` keeps inferring while the speaker is active, rather than
  ESPHome pausing it during playback.

If either fails, keyword barge-in as described does not function, and the
open-ended path (already deferred) becomes the only route. The implementing
change verifies both on a device before the renderer branching is relied upon.

**Consequences**

- The firmware renderer branches `on_wake_word_detected` on the matched model;
  the `stop` model during a running turn routes to `conduit_voice.interrupt`,
  everything else to `conduit_voice.start`. The checked-in fragments
  (`firmware/esphome/*.conduit.yaml`) regenerate accordingly, asserted by
  `firmware_fragments`.
- `Command::Stop` carries a reason discriminant distinguishing a button press
  from a heard keyword, defaulting to `UserRequested`. A satellite that does not
  send it behaves exactly as today — a test asserts the default path is
  unchanged.
- A keyword barge-in cancels the turn with `CancelReason::BargeIn`, TTS output
  stops, and the `barge_in` metric increments — asserted, not assumed. A
  button-press stop remains `UserRequested`.
- `crates/conduit-runtime/tests/turn.rs`'s
  `nothing_the_runtime_does_reports_barge_in` is **narrowed**, per ADR-0014:
  its existing endings must still assert non-barge-in, and a case is added in
  which a `stop`-model interrupt does produce it. It is not deleted or relaxed.
- The documented limitation is stated: the assistant saying the word "stop" can
  interrupt itself. `README.md`'s "Barge-in is not detected, only requested" gap
  is rewritten to "keyword barge-in is detected; open-ended barge-in is not".
- Open-ended energy-VAD barge-in, the duplex-audio protocol, the echo posture,
  and the fire threshold remain deferred to a future ADR, gated on #122.
- `ProviderCapability` and `NodeKind` are unchanged. Keyword barge-in adds no
  graph vocabulary; only the deferred energy-VAD path would, and it is not
  decided here.

**Open questions**

Deferred to the duplex-audio ADR, not decided here — unchanged from ADR-0014
except that the keyword path no longer waits on them:

- How does audio reach the server during playback? Still the blocking decision
  for open-ended barge-in, still a device-protocol change with a
  backward-compatibility story.
- Is an open-ended barge-in detector a graph node or a property of the source?
  The keyword path is neither — it is device routing — but the energy path
  still has to answer this.
- What ends a turn on open-ended barge-in: any detected voice, or voice
  sustained past a threshold, and under which echo posture?
